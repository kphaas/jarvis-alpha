## WHAT SHIPPED

### F-023 closed — Secret rotation system

**File:** `jarvis-alpha/scripts/rotate_secret.py`
**DB:** `alpha_secret_rotations` table + `v_secret_rotation_status` view
**Config:** `jarvis-alpha/scripts/secrets_rotation.json` (10 secrets configured)
**Node map:** `jarvis-alpha/scripts/node_ssh_map.json`
**Log:** `jarvis-alpha/logs/secret_rotation.log`

**Features:**
- `python3 rotate_secret.py <SECRET> [--dry-run|--delete|--force|--yes]`
- `getpass()` input — value never in argv, env, or shell history
- Atomic tmp+mv on each remote node
- sha256-first-12 hash verification post-write
- Service restart + health-check per secret config
- Postgres record per rotation (id, rotated_by, next_due_at, value_hash)
- Rollback via `.secrets.bak.YYYYMMDD`
- `requires_alter_role: true` refuses DB password rotation with manual steps (TD-134 to add full ALTER USER support)

**Migration:** `brain/db/migrations/20260421_140000_secret_rotations.sql`

**Gotchas discovered during build:**
1. Postgres `GENERATED ALWAYS AS` expressions must be immutable; `timestamptz + interval` is NOT immutable. Fix: use `DATE` type with `(rotated_at AT TIME ZONE 'UTC')::date + rotation_days`.
2. Migration runner reads from `brain/db/migrations/`, NOT `brain/migrations/`. Naming: `YYYYMMDD_HHMMSS_description.sql`.
3. Cursor auto-commits bypass `jarvisalpha_commit.sh` gates. Use `ALLOW_EMPTY_DEPLOY=1` to redeploy existing commits.

### 2 reusable cleanup tools built

**`scripts/audit_jarvis_core.sh`** — Verdicts each path under `~/jarvis/`:
- Checks: LaunchAgent plists (exclude .bak), crontab, running processes, 4 source repos
- Output: `path | LA:N | CRON:N | PROC:N | CODE:alpha=N,forge=N,family=N,standards=N | VERDICT`
- Modes: `--all`, `--details`
- Base64-encodes search patterns to avoid SSH arg-quoting issues with `|` alternation

**`scripts/archive_jarvis_core.sh`** — Archives paths:
- Modes: `--plan`, `--execute`, `--rollback`
- Reuses audit verdicts as source of truth
- JSON manifest log + ARCHIVED.md in archive root
- Base64-encodes file writes (zsh remote shell can't handle nested heredocs)
- Sanity checks post-execute: Brain health, LaunchAgent state, stack process count

## THIS SESSION'S SECURITY INCIDENTS (for future learning)

Two accidental leaks, both by me (Claude), one I caught and one Ken caught:

### Incident 1: bash -x trace (re-occurrence of TD-129)
When debugging SSH failure in archive script, I recommended `bash -x`. Script doesn't source `.secrets`, but the shell's startup sourced `~/.zshrc` which set `CLAUDE_CODE_API_KEY`. Trace dumped the value to conversation log.

**Outcome:** Ken revoked the Anthropic API key on console.anthropic.com. Dead string in logs, no exposure.

### Incident 2: grep -n showing file contents
When auditing `.zshrc` for `CLAUDE_CODE_API_KEY` cleanup, I used `grep -n` — which prints line content. Same key leaked a second time. Ken caught it.

**Outcome:** Key was already revoked from Incident 1. TD-143 created as permanent rule.

**Pattern:** I've repeatedly violated my own "never expose secret values" rules this session. New memory entry (#29) codifies: use `grep -l` (filename) or `grep -c` (count) only; `awk` with `=***` redaction; NEVER `bash -x` near shell init files or `.secrets`.
