## Critical Issues Discovered + Resolved Tonight

### 1. Brain Reliability Code Was Deployed But Not Committed

**Discovery:** After HANDOFF_01, ran `git status brain/routes/` on Air → "working tree clean". The Brain `watchdog.py` and `health.py` changes from earlier in the day had been edited via SSH heredoc directly on Brain's disk, NOT in the alpha repo. Tomorrow's `jarvisalpha_pull.sh` on Brain would have wiped the new code.

**Recovery:** SCP'd the files from Brain back to Air, verified they were the new versions (262 + 139 lines, contained POST endpoint and `_classify_agent_status`), committed via `jarvisalpha_commit.sh` as commit `d86b077`.

**Lesson learned:** Never edit files directly on a node via SSH. Always edit on Air (in the repo), then commit + auto-pull. The "deploy from tarball on Brain" pattern broke this rule and almost cost us the work.

### 2. Forge Reliability Files Had Same Problem

Same situation on Sandbox side. Files were SCP'd to Sandbox during the install, never committed to the forge repo. Cleaned up with the same pattern: SCP back to Air, verify, commit.

### 3. Sandbox Auto-Pull Collision (Resolved)

When we committed the forge reliability fixes, the auto-pull on Sandbox failed because Sandbox already had the SAME files as untracked. Git refused to overwrite untracked working-tree files with incoming committed versions (data-loss protection).

**Recovery procedure (now documented for next time):**
1. Verify byte-identical with `git show origin/main:path | diff - path` for each file
2. If identical, move untracked files to `/tmp/forge-collision-backup-DATE/`
3. `git checkout --` the modified-but-tracked files
4. `git pull --ff-only`
5. Verify pulled files match the backed-up versions
6. Verify no services were affected (the loaded LaunchAgents in `~/Library/LaunchAgents/` are independent of the source plists in `~/jarvis-forge/launchagents/`)
7. Cleanup the backup dir

**This recovery procedure should be added to PATTERNS.md as a known-good resolution.** Backlog item.

### 4. Forge Backlog Seed v1 Collision

The first SQLite seed run (`seed_backlog_2026-04-07.py`) tried to insert F-128 as the Brain costs.py fix. F-128 was already taken by "Planner LLM hour estimate tuning" — the seed correctly skipped it (idempotent), but that meant **the most critical P1 item didn't get logged at all**. Recovered by inserting it as F-137 in a v2 seed.

**Lesson learned:** Before seeding a backlog batch, query the DB for the highest existing ID to avoid collisions: `sqlite3 DB "SELECT MAX(CAST(SUBSTR(id, 3) AS INTEGER)) FROM features WHERE id LIKE 'F-%';"`

### 5. GitHub Issues v1 Script Failed (bash heredoc + label issues)

The original `create_github_issues.sh` used bash heredocs to embed markdown bodies. **Bash heredocs with `$()` and `${}` and quoted JSON inside markdown code blocks are extremely fragile** — the script broke parsing on the very first heredoc because bash tried to evaluate `$(api/...)` as a subshell.

It also tried to use labels that don't exist in the repo (`reliability`, `brain`, `observability`).

**Recovery:** Rewrote in Python with `subprocess.run(["gh", ...])` calls. Python multi-line strings don't have any escape issues. Only used the 3 standard repo labels: `bug`, `enhancement`, `documentation`. Worked perfectly on first try — created all 9 issues.

**Lesson learned:** **For any non-trivial gh CLI automation, use Python or another scripting language, not bash heredocs.** Add to PATTERNS.md.

### 6. Container File Persistence Issues

During tonight's session, the artifact-builder workspace had multiple stale state issues — files appearing/disappearing, directories getting renamed without intervention, tarballs containing wrong contents. Worked around by switching to inline `cat <<EOF` heredocs that you pasted directly into your terminal (not using tarballs at all).

**Lesson learned:** When the container workspace gets squirrelly, drop the tarball pattern and switch to inline-heredoc commands for the user to paste. Faster, more reliable.

**Why:** Tonight we manually built a one-off `make_issues.py` script to push 9 backlog items from SQLite to GitHub Issues. That script was hardcoded for those 9 items. We need a **reusable** version that syncs the SQLite feature_queue.db to GitHub Issues whenever the backlog changes.

**Architecture pre-locked from tonight's design discussion:**

| Concern | Decision |
|---|---|
| Sync direction | One-way only (SQLite → GitHub). Two-way deferred to F-138. |
| Source of truth | SQLite feature_queue.db is authoritative. |
| Deduplication | Match by `F-XXX:` prefix in GitHub issue title. Skip if exists. |
| Status mapping | SQLite `backlog`/`planned`/`in_progress` → GitHub `open`. SQLite `deployed`/`approved` → GitHub `closed` (optional flag). |
| Label mapping | SQLite `phase` → existing GitHub labels: `reliability`→`bug`, `ui`/`feature`→`enhancement`, `docs`→`documentation`. |

**Required CLI flags:**
- `--dry-run` — preview what would happen, no changes
- `--ids F-XXX,F-YYY` — sync only specific items
- `--status STATUS` — sync only items with specific status (default: `backlog`)
- `--close-deployed` — close GitHub issues whose SQLite status is `deployed`
- `--all` — sync everything (overrides `--status`)
- `--verbose` — show full diff for each item

**Pre-flight checks:**
- `gh auth status` — fail fast if not authenticated
- `sqlite3 db existence` — fail fast if DB missing
- Repo accessible — fail fast if `gh repo view` fails

**Reference implementation from tonight:**
- `~/Downloads/blv2/make_issues.py` — the one-off Python script that worked
- Uses `subprocess.run(["gh", "issue", "list", ...])` for dedup check
- Uses `subprocess.run(["gh", "issue", "create", ...])` for new issues

**Out of scope (defer to F-138):**

- Webhook-based real-time sync

## New Lessons / Patterns From This Session

### 1. Edit Discipline — Always Edit in Repo, Never on Node

**Rule:** Source files are edited in the repo on Air, never via SSH heredoc on a node. Even for "quick fixes". The deploy flow is always: Air commit → push → pull on node.

**Why:** Tonight we almost lost ~4 hours of Brain reliability code because it was edited directly on Brain via SSH `cat > file <<EOF` instead of in the alpha repo. The alpha repo's pull would have wiped it.

**The safety net:** Tonight we caught it because we ran `git status brain/routes/` BEFORE assuming the work was committed. Add this as a verification step in any tarball install procedure.

### 2. Tarball Install → Repo Commit Pattern

When deploying via tarball (forgefix, healthfix, etc.), the install script puts files in the right place on the node. **It does NOT put them in the repo.** Two-step process:

1. Tarball deploys to node disk + verifies the running process picks up changes
2. Air-side: `scp node:path/to/file repo/path/to/file` + commit

This should be documented as the canonical "tarball install workflow" in PATTERNS.md.

### 3. SQLite Backlog Seed — Always Check Highest ID First

```bash
sqlite3 ~/jarvis-forge/memory/feature_queue.db \
  "SELECT MAX(CAST(SUBSTR(id, 3) AS INTEGER)) FROM features WHERE id LIKE 'F-%';"
```

This one-line query saves you from F-128-style collisions when seeding new items.

### 4. gh CLI Automation — Python, Not Bash

For any non-trivial gh CLI automation involving:
- Markdown bodies with special characters
- JSON parsing of `gh` output
- Multiple labels or conditional logic
- Idempotent dedup checks

**Use Python with `subprocess.run(["gh", ...])`.** Bash heredocs WILL bite you. Tonight's `make_issues.py` is the canonical reference implementation — copy it for the sync tool.

### 5. Working Around Container State Issues

When the artifact builder gets squirrelly (files appearing/disappearing, dirs renaming themselves):
- Drop the tarball pattern
- Use inline `cat <<EOF` heredocs that the user pastes directly into their terminal
- The terminal is the source of truth, not the container workspace
- Faster and more reliable for one-shot scripts
