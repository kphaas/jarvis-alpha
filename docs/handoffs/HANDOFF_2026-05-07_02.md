## WHAT BROKE

### Symptom 1 — UI couldn't load

Browser console flooded with: `Fetch API cannot load https://jarvis-brain.tail40ed36.ts.net:8186/* due to access control checks`.

### Symptom 2 — DELETE thread returned 500

User-facing: clicking delete on any thread returned generic 500. UX broken.

Logs showed access entries with status 500 but **zero ERROR-level Python exceptions**. Bug was 9 days old (since 2026-04-28), reproducible, multiple retries.

---

## ROOT CAUSES

### Bug 1 — CORS port mismatch

UI accessed via default HTTPS (:443) but Brain CORS allow_origins locked to `https://jarvis-endpoint.tail40ed36.ts.net:4100` (exact match). Browser preflight rejected.

**Fix:** Bookmark on :4100 explicitly. CORS works.

### Bug 2 — Approval queue data corruption + buggy expire function

`alpha_approval_queue` had 11 stale rows including 3+2 duplicates for ken+empty-hash (sha256 of empty body = DELETE has no body).

`expire_pending_approvals()` PL/pgSQL function uses incorrect syntax:
```sql
UPDATE alpha_approval_queue
SET status = 'expired'
WHERE status = 'pending' AND expires_at < NOW()
RETURNING id INTO v_expired_ids;  -- fails with P0003 when >1 row
```

Result: 2 stale pending rows could never be expired. Function fails every minute, logs WARNING, never makes progress. New DELETE attempts piled into the corrupted queue.

**Tonight's fix:** TRUNCATE alpha_approval_queue + alpha_approval_audit CASCADE. Queue clean.
**Real fix (TD-201, next session):** Rewrite function with CTE + array_agg pattern.

## TONIGHT'S FIX

```sql
BEGIN;
TRUNCATE TABLE alpha_approval_queue, alpha_approval_audit CASCADE;
COMMIT;
```

After cleanup: DELETE in UI now returns canonical **403 with `approval_required`** (the intended T5 destructive flow). User approves via Approvals page → retries → succeeds.

## WHY THE BUG EXISTED 9 DAYS

- The 500 was happening but no Python ERROR was logged (asyncpg PostgresError didn't propagate through structlog cleanly)
- The expire function failure was logged only as WARNING, easy to miss
- alpha_brain_error.log was monitored but mtime stuck (asyncpg "Resetting connection" warnings not surfaced)
- Without observability into PL/pgSQL exception types, the bug was invisible until someone tried to use it

**Observability gap:** Structured logging needs to capture PostgresError subtypes (P0003, 23xxx, etc.) at ERROR level when they reach the route boundary, not just SQLState codes that go to stderr.

### What worked

- **Refusal to ship band-aids.** Multiple times path C (try/except wrap) was tempting; held the line until root cause was confirmed.
- **Manual psql reproduction** ruled out 4 bad hypotheses fast.
- **pg log + access log + structured log triangulation** eventually cracked it.

### What failed

- **Six wrong hypotheses** before finding root cause. Each rationalized with partial evidence. Should have grepped "approval" in pg log SOONER instead of filtering aggressively.
- **Initial fix attempt for handoff doc broke** because `jarvis_branch` (the new P-trait helper) doesn't switch branches as expected — used raw `git checkout -b` instead. Worth investigating in jarvis-standards.
- **Late session timing.** 7+ hours of debug, mistakes accumulated. Should have stopped earlier and slept on it.

### Big-tech principles applied

- **Read live state, not docs.** chat_threads schema, alpha_approval_queue contents, route handler code — all read from source of truth, not architecture spec.
- **Read library docs when behavior is unexpected.** PL/pgSQL `RETURNING ... INTO array` semantics required checking PG docs.
- **TRUNCATE CASCADE understands the FK graph** — let the DB tell you the dependency, don't guess.
- **Canonical fixes over tactical patches.** TD-201 is the proper fix; tonight's TRUNCATE just unsticks the immediate pain.
