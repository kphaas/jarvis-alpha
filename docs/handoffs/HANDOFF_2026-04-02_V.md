## TWO OPEN BUGS — FIX FIRST NEXT SESSION

### BUG 1 — Double Send (P1)

**Symptom:** User message bubble appears twice. JARVIS responds twice. Happens on first send in a new conversation, sometimes on council mode.

**What we tried:**
- sendingRef guard — didn't stop it
- isSending useState + sendingRef combined — didn't stop it
- e.stopPropagation() on Enter keydown — didn't stop it
- blur(document.activeElement) on send — didn't stop it
- 500ms timestamp debounce (lastSendTime.current) — NOT YET CONFIRMED working

**Current guards in ChatWindow.tsx (line ~41):**
```typescript
const now = Date.now();
if (!text || streaming || isSending || sendingRef.current || (now - lastSendTime.current < 500)) return;
lastSendTime.current = now;
setIsSending(true);
sendingRef.current = true;
```

**Diagnosis:** The message is added to state twice — meaning `send()` fully executes twice, past all guards. This is NOT a React StrictMode issue (production build). Most likely cause: the JARVIS shell's Layout.tsx or App.tsx has a keydown handler on a parent element that also fires, OR the textarea onKeyDown event propagates up to a form-like container. The guards all execute on the SAME React fiber — if two separate event handlers call `send()` from two different event sources (not just two firings of the same handler), refs won't stop it because they update synchronously but React batches state.

**Recommended next debug steps:**
1. Open browser DevTools → Sources → add breakpoint on `send()` first line
2. Press Enter once — check call stack. If it fires twice, the call stack will reveal the second caller
3. Check Layout.tsx and App.tsx for any global keydown handlers
4. As nuclear option: use `window.__jarvisSending` flag instead of React ref — truly global, survives any component tree
```typescript
// Nuclear option in send():
if ((window as any).__jarvisSending) return;
(window as any).__jarvisSending = true;
// ... rest of send
// In onDone and onError:
(window as any).__jarvisSending = false;
```

### BUG 2 — Council Panels Not Displaying (P1)

**Symptom:** "Show thinking" button appears on synthesis bubble. Clicking it doesn't reveal per-model panels. Panels worked briefly in earlier testing then stopped.

**What we know:**
- Backend confirmed working: SSE stream sends council_model chunks correctly
```
  data: {"council_model": "claude", "thread_id": "...", "done": false}
  data: {"delta": "Hi ", "council_model": "claude", "thread_id": "..."}
```
- council_detail IS embedded in synthesis chunks (council_summary variable)
- apiFetchStream correctly routes council_model chunks to councilAccum
- councilStreams state updates in ChatWindow

**Current panel logic in MessageBubble.tsx:**
```typescript
const isCouncil = !!msg.council_detail && Object.keys(msg.council_detail).length > 0;
const hasLiveStreams = !!msg.councilStreams && Object.keys(msg.councilStreams).length > 0;
const showPanels = (showCouncilPanels || showCouncil) && (hasLiveStreams || isCouncil);
const panelData = isCouncil ? msg.council_detail! : (msg.councilStreams ?? {});
```

**Most likely cause:** After streaming completes, `councilStreams` is set to `undefined` and `council_detail` is set from `councilDetail` in onDone. But if `councilDetail` (from apiFetchStream's `lastCouncilDetail`) is undefined, `council_detail` in the message is null — so both `isCouncil` and `hasLiveStreams` are false, and `showPanels` is false.

**Why councilDetail might be undefined:** `lastCouncilDetail` in apiFetchStream is only set when a chunk has `council_detail` field. The synthesis chunks embed council_detail on every word chunk. But if synthesis produces empty text (which happens when all council models return empty), the for-loop never executes and no chunk with council_detail is ever sent.

**Recommended next debug steps:**
1. Add console.log to onDone callback in ChatWindow: `console.log('onDone councilDetail:', councilDetail)`
2. Add console.log in MessageBubble: `console.log('showPanels:', showPanels, 'isCouncil:', isCouncil, 'council_detail:', msg.council_detail)`
3. Check if council models are actually returning non-empty text — if Claude/Gemini/Perplexity return empty, synthesis is empty, council_detail never streams
4. Quick test: manually set council_detail in the onDone handler using councilAccum if councilDetail is undefined

**Nuclear option fix in ChatWindow onDone:**
```typescript
(tid, finalModel, councilDetail) => {
    // If councilDetail not received from stream, use what we accumulated locally
    const finalCouncilDetail = councilDetail ?? 
        (Object.keys(councilAccum).length > 0 ? { ...councilAccum } : null);
    ...
    council_detail: finalCouncilDetail,
```
