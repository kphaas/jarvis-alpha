### The CRITICAL gotcha — self-cancelling rollback

After all 12 files committed and Brain pulled, the migration runner applied **two** migrations 104ms apart:

```
✅ 20260430_160900_slab2_guc_namespace_migration.sql applied (16:20:08.653)
✅ 20260430_160900_slab2_guc_namespace_rollback.sql  applied (16:20:08.757)  ← unintended
```

**Root cause:** runner (`apply_migrations.sh` line 129) globs `"$MIGRATIONS_DIR"/*.sql` — picks up every `.sql` in directory. Forward + rollback shared timestamp prefix, sorted lexically (`migration` < `rollback`). Both ran in same pass, second canceled first.

**Net effect during the gap:** code wrote `rls.*` GUCs, policies still read `jarvis.*` (after rollback re-applied old policies) → silent fail-closed for any RLS-protected query. Tests passed (133) because tests use admin context that bypasses RLS.

**Recovery:**
1. Quiesce services (same Slab 1 pattern)
2. Move rollback file to `brain/db/rollbacks/` (outside runner scan)
3. Manually delete BOTH rows from `schema_migrations`
4. Re-run runner — applied forward only (1 applied, 60 skipped, 0 failed)
5. Restart services in reverse dep order
6. Smoke test — all green

**Captured as TD-183 (CRITICAL):** rollback files belong outside `migrations/` directory; runner should also filter `*_rollback.sql` defensively (TD-184).

### Clean second deploy after rollback file relocation

Second commit (`31339c8`) committed the file move. Brain pull triggered with services already running — pulled clean fast-forward. Migration runner ran with 0 applied (just a file rename, no migration to apply). **The system's deploy pipeline now permanently safe against this class of bug.**
