## The New Endpoint

`POST /api/github/{project_id}/issues/create`

### Request

```json
{ "feature_id": "F-XXX" }
```

### Response (200)

```json
{
  "feature_id": "F-XXX",
  "github_issue_number": 33,
  "github_issue_url": "https://github.com/kphaas/jarvis-forge/issues/33",
  "repo": "kphaas/jarvis-forge",
  "label": "bug"
}
```

### Behavior

1. Resolves project_id → repo_slug via existing `_expand_local_repo_root` + `db.resolve_repo_slug` (uses `.forge/config.yml`)
2. Looks up feature by ID, scoped to project_id
3. **Refuses (409)** if feature already has `github_issue_number` set
4. Maps SQLite `phase` → GitHub label via hardcoded `PHASE_TO_LABEL` dict
5. Builds title as `{feature_id}: {feature.title}`
6. Builds body as `description` + `## Acceptance Criteria` markdown
7. POSTs to GitHub via httpx
8. On success: writes `github_issue_number` and `github_synced_at` to SQLite via new `db.set_feature_github_issue` helper
9. On partial failure (GitHub created, SQLite write failed): returns 500 with the manual SQL recovery statement

### Error paths

| Code | Trigger |
|---|---|
| 400 | Missing or empty `feature_id` in body |
| 404 | Project not found |
| 404 | Feature not found in project |
| 409 | Feature already linked to GitHub issue |
| 500 | GitHub API failure (passes through error text) |
| 500 | SQLite write failure after GitHub success (includes recovery SQL) |

### Phase → Label Map

```python
PHASE_TO_LABEL = {
    "reliability":   "bug",
    "observability": "enhancement",
    "ui":            "enhancement",
    "feature":       "enhancement",
    "docs":          "documentation",
    "documentation": "documentation",
}
```
Default: `enhancement` if phase is None or unknown.

## Tonight's Critical Discoveries

### Discovery 1 — Per-Node SQLite Drift (F-140)

`feature_queue.db` is gitignored and lives independently on each node. Air has its own copy, Sandbox has its own copy. The commit script never syncs them. We spent ~30 minutes recovering from editing Air's DB while forge service on Sandbox was reading a completely different DB.

**Symptom:** New endpoint returned `Feature F-139 is already linked to GitHub issue #28` when SQLite (Air's copy) had F-139 with NULL github_issue_number. Sandbox's DB had 88 rows of corrupted state from prior failed seeds, including an F-139 row with stitched data from F-135.

**Recovery:** Stop forge → snapshot Sandbox DB → SCP Air DB → sha256 verify → start forge → re-test. All 9 verify gates passed.

**Lesson:** **All forge SQLite edits must happen on Sandbox** (where forge reads from) OR be SCP'd over with an explicit verification step. F-140 will build the scripts.

### Discovery 2 — `sync_github_issues` Has Two Bugs (F-138)

Tested existing `/api/github/2/issues/sync` end-to-end. API returned `{"inserted":9, "updated":20}` but SQLite total was unchanged at 50.

**Bug A:** Counter variables swapped — what it called "inserted" was actually updates.
**Bug B:** Insert branch silently fails. Most likely: `INSERT OR IGNORE` swallows PK collisions because `next_num` is computed from an uncommitted transaction (the SELECT for max F-id returns the same value for every iteration in the loop).

**Impact:** Low. UPDATE branch is safe (only touches `title, status, github_synced_at`, never `description` or `acceptance_criteria`). Pull-sync technically works for already-linked features but cannot import new GitHub issues.

**Mitigation:** Tonight built `POST /issues/create` as a clean parallel codepath — does not share `sync_github_issues` logic.

But the file already had the new values (from this morning's rls commit). ## Lessons / Patterns From This Session

### 1. Always check state before assuming

Earlier-in-session assumption: "Brain is on d86b077 with uncommitted edits per last night." Reality: Brain was on `adeb3f4`, 5 commits ahead, and the F-137 fix was already deployed. **Rule:** Discovery prompts before any deploy prompt. No exceptions.

### 2. Edit forge SQLite on Sandbox, not Air

The forge service runs on Sandbox and reads its local `~/jarvis-forge/memory/feature_queue.db`. Air has its own copy that is gitignored and never synced. **Rule:** Always do forge SQLite edits via `ssh jarvissand@... "sqlite3 ..."` until F-140 sync tooling exists.

### 3. After str_replace, verify with git diff

Cursor str_replace can return success when the file content was already in the target state. The replace happens, but it is a no-op. **Rule:** After every str_replace, run `git diff path/to/file`. If diff is empty, stop and investigate.

### 4. Use gh CLI for GitHub data, not web scraping

When the agent needed real GitHub issue bodies, the right tool was `gh issue view --json body` on Cursor's local terminal (gh is already authenticated). Not web_fetch (permissions issue), not bash heredocs (escape hell). **Rule:** For any non-trivial GitHub data fetch or write, use `gh` CLI with JSON output.

### 5. Pull issue bodies from source of truth, not handoff notes

Tonight's Step 2 originally tried to re-seed F-129..F-137 from descriptions reconstructed from last night's handoff. The reconstructions were directionally correct but missing specific URLs, full acceptance criteria, and code references. Pulled the real bodies from GitHub Issues via gh CLI instead. **Rule:** When data exists in two places, fetch from the more authoritative source.

### 6. Build new endpoints as clean parallel codepaths when existing functions are buggy

Tonight could have tried to fix `sync_github_issues` to support reverse direction. Instead, built `POST /issues/create` as a parallel function that does not share `sync_github_issues` codepath. Cleaner separation, faster delivery, no risk of breaking the (working) existing pull path.
